# /mr <задача>

Незакоммиченная работа → MR. Форж, схему имени ветки и формат subject бери из `CLAUDE.md` проекта, чего там нет — спроси один раз.
`<base>` — обычно `dev`; нет такой ветки — дефолтная ветка репозитория (`git symbolic-ref refs/remotes/origin/HEAD`) или то, что задано в `CLAUDE.md`.
Номер задачи не передан — спроси: текущая ветка может быть от **другой** задачи.

## 1. Разведка

```bash
git status --short && git branch --show-current && git log --oneline <base>..HEAD
```

**Авторизацию CLI форжа проверь здесь, а не на шаге 4.** Обычно в окружении есть `glab` — начинай с него, иначе `gh` или что стоит у проекта. Авторизация регулярно есть для публичного хоста и отсутствует для self-hosted, а выяснится это когда ветка уже запушена. Нет — ищи в проекте REST-обёртку/токен и переключайся сразу.
Достань summary задачи и сверь с диффом: задача про одно, а в дереве другое — стоп, спроси.
Отдели файлы задачи от локальных артефактов (выгрузки, отладочные скрипты, таблицы) — вторые в MR не идут, и `git add -A` тут не годится, только явные пути.
`git log <base>..HEAD` показал коммиты **другой** задачи — в новый MR они не попадут, но скажи юзеру явно, сам не решай.

## 2. Ветка от свежей базы

```bash
git stash push -u -m "<задача> wip" -- <файлы задачи>   # явный список: артефакты остаются в дереве
git switch <base> && git pull
git switch -c <branch>
git stash pop
```

**Конфликт при `pop` — ожидаемое событие**, база ушла вперёд. Где правки аддитивные (`.gitignore`, манифест зависимостей) — оставляй **оба** блока.
Stash после конфликтного `pop` не удаляется — страховка; `drop` только убедившись, что всё на месте.
Ветка уже была и отстала от базы — подтягивай **merge**, не rebase: rebase переписывает историю, уже отданную в MR, и ломает ссылки в обсуждении.

```bash
git switch <branch> && git merge <base>    # не rebase
```

Прогони проверки проекта (линтер, быстрые тесты — команды из `CLAUDE.md`/конфигов) **после** `pop`: база изменилась, зелёное до среза ≠ зелёное после. Числа пойдут в описание MR.

## 3. Commit

`git commit -F-` с heredoc, не `-m`: не ломается на кавычках и переводах строк.
**Subject** — по формату проекта (обычно `<задача> <type>: <название задачи из трекера>`). `<type>` бери по сути диффа, а не по типу тикета: багфикс-тикет, добавивший поле в ответ, — это `feat`. История базовой ветки неоднородна — это legacy, не ориентир.
доBody — что и зачем, 1-2 абзаца. Без «Test plan» и трейлеров.

## 4. Push и MR

```bash
git push -u origin HEAD          # без --force, никогда не в базовую напрямую
```

Ревьюера назначай, только если проект его требует и правило назначения известно — **себя не ставь**. Аргументы вызова перебивают. Не знаешь, кого ставить — создавай без ревьюера и скажи об этом.
MR — командой форжа, описание файлом или heredoc, не аргументом-строкой. Перед созданием покажи превью (source → target, title, ревьюер, разделы описания) и дождись подтверждения.

### Описание

Для человека, который дифф не читал. Не пересказ коммита:

- **## Задача** — идентификатор + что требовалось.
- **## Что сделано** — по смысловым блокам, не по файлам: что изменилось и **почему именно так**, конкретикой — какой вход раньше давал какой неверный выход.
- **## Breaking change** — что удалено, как ломается клиент, предложение.
- **## Открытые вопросы** — где решил за постановку, с пометкой «не подтверждено».
- **## Проверено** — числа тестов, статус линтеров, и **что проверить не удалось и почему**. Прошлый прогон за текущий не выдавай.
- **## Не в скоупе** — что осознанно не починил, где фикс.

## Границы

Трекер (комментарий, reviewer, статус) — только по подтверждению: дёргает чужие уведомления. Свой MR не мержишь и не аппрувишь.
Отчёт: ссылка на MR, ветка, хэш, `N files changed`, числа проверок и что **не** делал.
